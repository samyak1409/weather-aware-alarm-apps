# weather-aware-alarm-apps monorepo

Two Flutter alarm apps sharing one core package. **Read SPEC.md before changing any behavior — every product decision there is locked with Samyak; don't silently re-decide.**

## Layout

- `packages/core` — pure logic: solar math, sleep plan, wind engine, Open-Meteo client, theme, models, repos. **All business logic lives here, fully unit-tested.** Apps stay thin.
- `apps/arunoday` — dawn alarm app (daily driver, priority app).
- `apps/nivaat` — wind-conditional badminton alarm.

## Conventions

- UI: pure black `#000000` scaffolds / app bars, dark-only, minimal. Accents: Arunoday `AppPalette.dawn`, Nivaat `AppPalette.wind`. Elevated overlays (sheets / dialogs / snackbars / `DropdownButton` menus / `showTimePicker`) use `AppPalette.surface` (`#0E0E0E`) — menus via theme `canvasColor`; time picker via `timePickerTheme` + pinned `ColorScheme.surfaceContainer*` (ignores `dialogTheme`); `surfaceTint` off (2026-07-23). No third-party UI kits.
- **Design pass (2026-07-20, Samyak's premium-feel round)**: (1) hero type — ships THIN (the original look); the Settings toggle "Bold clocks & titles" (`Appearance.heavyType`, persisted, default OFF) switches `buildOledTheme(heavyType:)` to w700/w600 heroes with tabular figures; body/labels stay w400 in BOTH modes (the weight contrast IS the look — don't bolden the quiet styles; locked by `design_test.dart`). Each app's `MaterialApp` rebuilds live via `ValueListenableBuilder` on `Appearance.heavyType`. (2) `CraftedBy` (core) renders `CRAFTED WITH ♥ BY SAMYAK` at the foot of BOTH home screens — the heart is `Icons.favorite` (NOT a text glyph: Android font fallback promotes text hearts to the baked-red emoji — device-caught), tapping SAMYAK opens `craftedBySiteUrl`, and seven taps on the mark toggle `DevMode` (see the developer-gate bullet). (3) All motion runs 50% slower: `applyMotionPacing()` (core `motion.dart`, `kMotionSlowdown = 1.5` via `timeDilation` — verified release-safe in Flutter source, it's a plain runtime scale) called at the top of both mains; experiment, revert = delete those two calls. Both Info.plists already had `CADisableMinimumFrameDurationOnPhone` for 120Hz ProMotion. (4) **Launch screens are black** on both OSes (Android `launch_background*.xml` + `Theme.Black` styles, iOS storyboard bg) — never reintroduce the template white. (5) **Portrait-only (2026-07-22)**: landscape overflows home/sheets/dialogs — lock via Android `screenOrientation="portrait"`, iOS Info.plist portrait-only (phone + iPad) + `UIRequiresFullScreen`, and `lockToPortrait()` in both mains; don't re-enable landscape without a layout pass.
- **Developer settings are hidden behind seven taps on the maker's mark (2026-08-06, Samyak)** — core's `DevMode`, shared by both apps, persisted, ships OFF; the toast says which way it went (X8). **The tap surface is the whole padded footer, not the heart alone**, and that is deliberate rather than sloppy: the mark is one 10px line, so an 11px icon is a target no thumb can hit seven times, and `HitTestBehavior.opaque` over the padding that was already there costs no layout. SAMYAK stays a link inside it because its `RenderParagraph` sits deeper in the tree and so enters the gesture arena FIRST — `dev_mode_test` taps SAMYAK seven times and asserts the gate stays shut, and that assertion is not vacuous: deleting the recognizer by hand during review made those same seven taps flip it. **What it gates today is one option**, Nivaat's 1-minute *Keep checking* window (`CheckCascade.devRetryMinutesOptions`), and it is written as a switch because more will follow. **The gate decides what is OFFERED, never what already works:** `retryOptionsFor` always includes the alarm's current value, so an alarm saved at 1m still shows 1m after the gate closes (a control with nothing selected misrepresents the alarm), and the engine honours a stored 1 either way. The message is core's `showAppToast` — an overlay pill, **not a `SnackBar`**, because the Scaffold parks a floating snackbar at `floatingActionButtonRect.top` and Nivaat's home has a FAB while Arunoday's does not, so one call landed 72 pt apart in the two apps (measured; neither `margin` nor `width` can push it back down). It also sizes to its text, which a snackbar cannot. It is **centred on the mark's own measured middle** (a `GlobalKey` on the line, not the widget box — that one carries the padding) so it reads as that line's answer, and therefore **pointer-transparent**: covering what raised it, its Material otherwise ate the next seven taps until it faded, which a test now catches. **A run of taps expires after `DevMode.tapGap`, one second (Samyak, 2026-08-06, down from two)** — the mark is on screen all day, so without a window stray taps accumulate for a week and flip the switch with nobody meaning to, and deliberate taps land 150-300 ms apart so a second is already several times the room anyone needs. Pinned by a test: don't widen it to answer a "the taps don't register" report. **Both mains must `await DevMode.load()` before `runApp`** or the gate silently forgets itself every launch with no error anywhere; `startup_parity_test` (arunoday, reads both mains) locks that for `DevMode` and `Appearance` together.
- **Nivaat navigation (2026-07-20)**: the home top bar has ONE entry point — the settings (tune) icon; courts, alarm sound, and history are settings tiles (that order), and home shows a live `Still checking wind · until HH:MM` cue (tap → history) only while a per-alarm retry window is open (2026-07-22 — replaced the permanent last-outcome dump; cap is 30/60 min per alarm since 2026-07-26, plus a dev-gated 1 since 2026-08-06). Enabled home rows (+ alarm editor under the clock) show sentence-case `in {Xh Ym}`, or `in {Nd HHh}` past a day (wall-clock :00 ticks, re-aimed on resume — never `Timer.periodic`, which drifts by however long the app was suspended; not Arunoday ALL-CAPS; hidden during that alarm's post-T retry — editor still counts down to the draft clock mid-window / when switched off: picker feedback). **One card per morning (2026-07-26)**: a single notification (`NivaatIds.card`, the old 40000 heads-up block) posts at T as `Still checking` and is REWRITTEN in place to `Skipped` / `Cancelled` — there is no second card, and the old 50000 skip block is gone (nothing sat above it, so no renumbering; a card already posted under the old meaning is not a case this repo carries — see the no-migration bullet). Every push **alerts** — no quiet variant, no per-platform presentation flags. Cancelled only by a late ring (the ring becomes the card), delete, or court-gone; a toggle-off or abandoning edit rewrites it to `Cancelled` instead, since the alarm still exists. Mid-window **continue** edits (limit, Keep checking, add-only weekdays) keep today flying; a Keep-checking change re-posts the card with the new deadline built from the STORED reading — never rebuilt from the edited alarm, which put new limits beside the old numbers ("Too windy · wind 5 (≤20)"). **`retainInFlightEdits` must check BOTH windows (2026-07-31):** the old one (widening after death must not resurrect a morning) *and* the new one — shrinking 30→1 at T+2 checked only the old, so it re-posted an ALERTING card promising `watching until 06:01` at 06:02 plus an immutable row to match, the exact broken promise the one-card model exists to prevent. Both dead-window paths now go straight to `_finaliseDeadWindow`; `morning_story_test` 14d locks it, including the general rule that no row may promise a deadline already past when it was written. Don't re-add top-bar icons. Arunoday's settings rows are grouped by ritual: wake pair, bedtime group, shared sound, then APPEARANCE, then LOCATIONS. Both settings pages scroll as ONE surface (2026-07-20) through core's `FlashingScrollbar` (the flash-on-open-if-overflowing cue) — no inner scroll regions. **Nivaat home alarm list** also uses `FlashingScrollbar` (2026-07-22). **Nivaat unique HH:MM** (2026-07-22): no two alarms share the same clock minute (court/weekdays ignored; ±1 min for multi-court); N18 inline + `upsertAlarm` returns `false` on conflict.
- **App icons (shipped 2026-07-20, switchable)**: all three candidates per app ship; Settings picker drives core's `app_icon.dart` over the `core/app_icon` MethodChannel (ids "1"/"2"/"3"; defaults Horizon/Shuttle). The picker ring updates optimistically — iOS runs the set-icon completion only after its system alert is dismissed — and reverts if the platform refuses. Sources: `branding/` + `tools/make_icons.py` (numpy SDF renderer); `--apply` rewrites the real launcher assets (Android adaptive mipmaps, iOS appiconsets, Settings thumbnails) — never hand-edit those PNGs. Android: MainActivity keeps the MAIN/LAUNCHER intent-filter + default icon (moving it onto aliases breaks `flutter run` after a clean — the tool's pre-build manifest parse only reads real `<activity>` tags); `.IconTwo`/`.IconThree` aliases (manifest-disabled) carry the alternates; switching flips component-enabled states with `DONT_KILL_APP`, safe because the `alarm` + `flutter_local_notifications` plugins resolve entry points via `getLaunchIntentForPackage` (verified in their sources). **Android closes the app on every switch and that is not fixable here (2026-08-01)**: the component being disabled is always the one the running task was launched through, so Android tears the task down — `DONT_KILL_APP` spares the *process*, not the activity, and the intent-filter can't move off `MainActivity` (above). So the picker **says so first on Android** (X7's `CHANGE APP ICON` notice, `appIconRestartWarning`); unannounced the close reads as a crash. It **informs rather than asks** — one `OK`, no Cancel — which makes the dismissible barrier the only way out and therefore load-bearing, and its paddings are pinned tighter than M3's (locked by `design_test`). `MainActivity` then **closes the app itself** (`finishAndRemoveTask()` after a successful `setIcon`, both apps, keep in sync): Android would anyway, but the beat it took read as a freeze. `setIcon` also skips disabling entries already off — only one is ever on and each redundant call is a binder round-trip the user waits through; still a loop, so corrupt two-on state resolves. **iOS must never get that dialog**: `setAlternateIconName` keeps the app running and the OS shows its own alert, so ours would be one more thing to dismiss. The platform split uses `defaultTargetPlatform` (not `Platform.isAndroid`) precisely so both branches are testable on the host. iOS: `AppIconTwo`/`AppIconThree` appiconsets + `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES` in every build config; the OS confirms switches with its own alert.
- Alarm scheduling goes through `core`'s `AlarmScheduler` interface, chosen by `createAlarmScheduler`: **`AlarmKitScheduler` on iOS (min target 26.0)**, `AlarmPkgScheduler` on Android. **iOS is AlarmKit-only — there is NO `alarm`-package fallback** (2026-07-18): if the user denies AlarmKit, `scheduleRing` silently no-ops (`PlatformException` caught) and `AlarmPermissionBanner` (shown on both home screens, driven by `alarmSchedulingDenied()`) nudges them to Settings via `url_launcher` (`app-settings:`). So `AlarmPkgScheduler` is effectively Android-only (`warningNotificationOnKill: false` — Android's ring genuinely survives kill). **Both wake and bedtime rings use AlarmKit on iOS** (2026-07-16: a real system alarm that survives force-quit/reboot beats the `alarm` package's in-process Timer; cost — Arunoday's bedtime "+1h" ritual is **Android-only**, since AlarmKit alerts are Stop-only). Never call the `alarm` package directly from screens, except ring-screen `Alarm.ringing` listeners. (AlarmKit's auth prompt is simulator-verified; real-device iOS ring behavior is still untested.)
- **Scheduler / notification id blocks — don't "tidy" them smaller (2026-07-26)**: every id is `block + index`, decodable by division (`id ~/ width` = which namespace, `id % width` = which alarm/slot). **Rule: the block width must exceed the largest index it can ever hold, with room to grow.** Arunoday: 1000-wide blocks over `ArunodayIds.slots` day-slots (1000 wake, 2000 bedtime, 3000 bedtime-again; `isBedtimeAlarm` = 2000..3000), each keyed on the alarm's **calendar day** so a given day's alarm keeps one id no matter when the resync runs. Nivaat: 10000-wide blocks over alarm ids (10000 ring, 20000 late ring, 30000 wind check, 40000 the morning's card, 50000 the roll-on pre-arm). The 50000 skip block was **removed** with the one-card model (2026-07-26) — nothing sat above it, so nothing renumbered — and 50000 was **reused** for `nextRing` on 2026-08-05, a deliberate reuse of a freed number (nothing sat above it, so nothing renumbered; a card already posted under the old meaning is not a case this repo carries — see the no-migration bullet). Both maps live in one file per app (`lib/src/ids.dart`) with an `ids_test.dart` that asserts no two ids ever collide — add new numbers there, never inline. **Nivaat's alarm ids come from a PERSISTED counter (2026-08-05, REVIEW #9 · #21)**, `nivaat.alarmIdSeq`, advanced and saved by the same `upsertAlarm` call that persists a new alarm — so a number is spent whether or not that alarm survives. "Highest + 1" handed a deleted alarm's number straight to the next one created, and since every id here is `block + alarmId` the new alarm inherited the old one's ring, late ring, check, card and cascade state. Two rules come with it. **`nextAlarmId()` must stay pure** — the alarm sheet asks once for the live HH:MM conflict check and again for the alarm it saves, and if asking advanced the counter those two would disagree, validating one alarm and writing another. And **it never hands out a number a live alarm already holds** — one rule, two reasons. Past `maxAlarmId` because a counter that only climbs makes the block ceiling *more* reachable, not less (#21). And because `upsertAlarm` reads a colliding id as an EDIT, so a counter somehow standing on a live alarm would make "add alarm" silently replace the one already wearing that number — the loudest possible bug arriving as the quietest. There is always a free number to fall back to, since N18 forbids two alarms on the same HH:MM and so caps coexisting alarms at 1440. **The counter is saved BEFORE the alarm that spends it, and that ordering is the whole guarantee.** Interrupted between the two writes, the counter is ahead of an alarm that was never saved and one number is skipped, which costs nothing; the other order leaves an alarm with no counter past it, and the next alarm created takes its number and overwrites it — ring, late ring, check, card and cascade state included. **Nothing re-derives the counter from the alarm list afterwards to paper over that** (`_reload` reads the stored value or starts at 1): "highest + 1" IS the bug, and a recovery path spelled that way brings it straight back, since deleting the newest alarm drops the highest with it. That was the pre-counter migration path, it never persisted what it computed, and it therefore reissued a live id on the next cold start — see the no-migration bullet above. **Nivaat's three ring lockers are split by ROLE — the pre-arm for an occurrence's own time, a LATE ring armed after T, and the pre-arm a ROLL-ON writes for the next occurrence.** One pass routinely closes an occurrence and opens the following one, and writing a ring evicts whatever its locker held (`Alarm.set` stops the same id first — `alarm 5.6.0`, `lib/alarm.dart:113`), so each thing that can be live at that instant needs its own number. Two bugs, one shape: with a single locker the next occurrence's pre-arm cancelled a **late ring** ~10s before it sounded (fixed 2026-07-26 by `lateRing`), and it cancelled the **pending ring for T itself** whenever the T-0 wind check won its race with the ring — an unwinnable coin-flip on Android, where both are exact alarms for the same instant — while history logged "Rang" either way (fixed 2026-08-05 by `nextRing`; REVIEW #1(a)). Four rules come with the split: arming a late ring must `cancel` the pre-arm it supersedes (else the alarm sounds twice seconds apart); a skip must cancel **only** the pre-arm lockers, never the late one (clearing that would re-create the 2026-07-26 bug); a roll-on (`_evaluate(rolledOn: true)`, reached only from `_rollOn`) must **never write or cancel `NivaatIds.ring`** — that locker belongs to the occurrence it just closed, which may still be milliseconds from sounding — and the occurrence's own first ladder rung then hands `nextRing` over to `ring`, cancel-then-set (set-then-cancel leaves two live alarms for one instant); and Rule 1 must test `isRinging` on **all three** lockers *and* gate its "rang" row on `!t.isBefore(stored.alarmAt)`, or a resync during a late ring logs *tomorrow* as rang. **A roll-on pre-arm can sound from `nextRing` directly** — that is the point of it on iOS, where no background slot may ever be granted before T — so it is never merely a staging copy that something else is guaranteed to move. **Do not "simplify" this to day-parity** — it looks equivalent and silently fails whenever consecutive occurrences are an even number of days apart (a Mon+Fri alarm is 4 days, same parity, collision returns). **Why not compact these to 10/20/30:** with a 10-wide block, bumping `windowDays` 7→14 puts wake id `10+13 = 23` inside the bedtime block, so `isBedtimeAlarm(23)` turns true for a WAKE alarm and the ring screen offers "+1h not sleepy" at dawn — a silent break from a one-line change that looks safe. The blocks cost nothing: these ids are ephemeral (recomputed every resync, never persisted as user data). **And two offsets are load-bearing, not cosmetic:** the `alarm` package posts its ring notification with `startForeground(id, …)` — i.e. **its Android notification id IS the alarm id** — so a skip/heads-up card sharing that number would erase the ring's own card and Stop button. Verified in the plugin's Kotlin (`AlarmService.kt`), not inferred.
- **Scheduling that fails must never read as success (2026-08-05, REVIEW #2 · #22).** `AlarmScheduler.scheduleRing` and `CheckScheduler.scheduleCheck` both return `bool` now, and **a caller that records "scheduled" must check it** — silently returning was how Nivaat came to log `Rang` for a morning nothing was armed for. Three parts. (1) **iOS**: `AlarmKitScheduler` caught its `PlatformException` and returned as if it had worked; it returns `false`. (2) **The engine follows the RING, not the verdict** — `armedWith` (the reading behind a ring really put on the platform) replaces `decision.shouldRing` as the gate on both `ringScheduled: true` and the at/past-T "rang" row; an unarmed occurrence is left OPEN so the remaining ladder rungs retry, and at T it falls through to the watching card rather than vanishing. (3) **`AndroidCheckScheduler` falls back to an INEXACT wakeup** when the exact booking is refused (the likeliest cause is exact-alarm permission, which an inexact alarm doesn't need — the same strategy the `alarm` plugin uses for its own rings): a check a few minutes late still decides the morning, a cascade that stopped booking decides nothing ever again. Soft-fail stays — one alarm's refusal must not cost its neighbours their evaluation — but it is now reported and logged with what was lost. **`true` means armed on Android from alarm 5.9.0** (upstream #420 closed via #422): a failed native schedule unsaves and throws. **It is still not Rang proof** — schedule success only means the ring is OWED; what finalises history is the settle, through `pendingRing` (2026-08-08). **And what a vanished ring MEANS is a per-platform fact, carried by `AlarmScheduler.reportsHostEvents`.** Android reports host moves and drops on `Alarm.events`, so a ring that is gone with nothing said about it is a real anomaly and the row reads `Couldn't confirm`. AlarmKit reports nothing it does on its own, and an alarm leaves it the moment it fires and is dismissed — which is what an ORDINARY morning looks like — while AlarmKit also never opens the app, so Nivaat is almost never running to see the ring as audible. Read the same way on both, iOS labels **every** ring unconfirmed; `_vanishedRingDisposition` is the one line that decides it, and `NoEventRing` vs `FakeRing` in `host_event_test` is the A/B that pins both answers. **The settle itself still runs on every platform** — skipping it on iOS left the pending on disk forever and the morning recorded nowhere at all, which is worse than the wrong word. The `FakeRing.accepts` / `FakeChecks.accepts` flags drive all of this in `engine_test`. **`IosCheckScheduler.cancelCheck` is a deliberate no-op (2026-08-05, REVIEW #8)** and must stay one: there is exactly ONE BGProcessing task for the whole app — iOS task ids are a fixed list in Info.plist + AppDelegate, so they cannot be minted per alarm — and cancelling it for one alarm took away every other alarm's near-T wakeup (disable the 06:00 at 05:40, the 07:00 loses its next check too). A reference count is **not** the fix either: a fresh isolate evaluating one alarm starts with an empty set and would cancel anyway. Not cancelling costs nothing worth having, because the submission is one-shot — a task nobody needs fires once, finds nothing to do, and is gone, so it can neither accumulate nor outlive the alarms. `check_scheduler_test` proves it by reaching for the plugin being fatal on the host (`UnimplementedError` is an Error, so the Exception guards do not swallow it), with `scheduleCheck` as the control that keeps the assertion from passing vacuously. Android is genuinely per-alarm and still cancels.
- **A deleted Nivaat alarm must never stay armed — and the cascade cannot fix that after the fact (2026-08-05, REVIEW #23).** `evaluateAll` reads the alarm list ONCE and then spends seconds per alarm on a wind fetch, with the home screen already up (`init` renders before it awaits `resync`), so a delete genuinely lands while the loop holds a stale still-`enabled` copy. Arming that copy's ring is **permanent**: `evaluateAll` only ever visits alarms that are in the store, so nothing looks at that id again and the ring fires on schedule for good. Two halves, both load-bearing, both proven by reverting them one at a time. (1) **`NivaatEngine._stillLive`** re-reads the store — alarm AND its court, since `removeCourt` is the same hole by the other door and the stale snapshot still lists the court, so `_evaluate`'s court-gone branch never fires — at the **point of no return**, after the fetch and before the first side effect. On entry is not enough: an evaluation already past that point schedules anyway. Consequence for tests: **an alarm that was never in the store is a fixture production cannot produce**, so `engine_test`'s `setUp` seeds one the way `morning_story_test` always did. (2) **`_sweepOrphanRings`** cancels every armed ring whose alarm has left the store, at the TOP of `evaluateAll` (behind the loop it would be skipped by any pass that throws). It is the only thing that reaches a ring already armed — by a build without the guard, or by a background isolate racing this one, which no check-then-act can close because SharedPreferences has no cross-isolate lock. **This is the one place Nivaat may read `scheduledIds()`**: a sweep decides what to CANCEL, and cancelling something already gone is a no-op, so its Android over-reporting is harmless *here and nowhere else* — never read it as proof a ring IS armed (REVIEW #2). **Nivaat being the first caller forced REVIEW #4 to be fixed first (2026-08-05):** `AlarmKitScheduler.scheduledIds()` used to prune every UUID whose state was not `scheduled`, which on iOS meant a sweep during a live ring purged the ALERTING alarm's mapping and left `isRinging`/`cancel` unable to reach it. It now prunes only what AlarmKit no longer knows at all, and only writes the map when something actually went. **Every cancel in the sweep is guarded individually**, because the sweep runs BEFORE the loop: one throwing id escaping it aborts `evaluateAll` with no alarm evaluated — the net taking down what it protects. `UncancellableRing` (scoped to specific ids, so it doesn't also break `_evaluate`'s own cancels, which may abort their own alarm's pass) locks it. **`_stillLive` calls `store.refresh()` first**: SharedPreferences caches per isolate, so without it a background check never sees a delete the UI just made — the exact split #23 is about. `StaleUntilRefreshedStore` is the only way to prove that: every other test shares one cache, so it passes whether or not anything refreshed. **The same reload was owed to `AlarmKitScheduler._loadMap`** (REVIEW #7's named gap; the race is narrowed, not closed — read-edit-save is still not atomic). **And REVIEW #6 needed BOTH halves to mean anything:** `cancel` keeps a UUID unless `cancelAlarm` really returned `true` (it signals failure by return value as well as by throwing), *and* `scheduleRing` must not then write the replacement over it. That second half was impossible while an id held exactly one UUID, and **it is done — the map holds a list now; see the AlarmKit bullet below (REVIEW #4 · #5 · #6, 2026-08-05).** `alarmkit_scheduler_test` mocks the plugin's `flutter_alarmkit` channel, so all of this is locked off-device; `alarm_launch_kotlin_test` (arunoday, reads both Kotlins) locks the launch token's rules including that it clears in `onStop` — Recents delivers no intent, so nothing keyed on one can clear it. It decodes ids through `NivaatIds.alarmIdOfRing`, which returns null for checks and cards on purpose: cancelling by a number that means something else is worse than missing a sweep. Orphan **checks** need no equivalent — a check wakeup for a missing alarm evaluates nothing and so never re-books itself, and dies after one firing.
- **Never destroy an alarm you have not replaced, and never cancel one you can hear (2026-08-05, REVIEW #3 · #4 · #5 · #6).** Two apps, one rule, arrived at from opposite ends.
  **Arunoday** has two paths that disarm — the resync sweep and "the last location is gone" — and only the first checked `isRinging`, so deleting your last location while the bedtime alarm sounded stopped the sound. They are **one method** now (`_cancelExcept(keep)`); a ringing id is never in `keep` (its moment is past), so the guard has to live in the shared path or not at all. A second copy would only have been a second thing to forget.
  **iOS**: `AlarmKitScheduler`'s map is `int id -> LIST of UUIDs`, newest first, and that shape is the fix — one UUID per id could not hold "keep the old handle when its cancel fails" (#6) and "create the replacement before destroying what it replaces" (#5) at the same time, because both want the slot. Four rules follow, and each is locked by `alarmkit_scheduler_test`. (1) **`scheduleRing` schedules FIRST**, then cancels what it superseded — a create that fails now leaves the old alarm armed and named, where cancelling first left the day silent with nothing on screen to say so. **The accepted trade is the mirror image:** a cancel that then fails leaves two live alarms for one id and both sound. A duplicate alert is a nuisance you can stop; a silent morning is the failure this app exists to prevent — do not "tidy" the order back. (2) The new UUID is **saved before** the cancels run, so a crash in the gap leaves an alarm we can still name. **The window that remains is create→save, and it is irreducible:** AlarmKit mints the UUID, so there is nothing to record until `scheduleOneShotAlarm` returns, and a process death between that return and `_saveMap` leaves an armed alarm no map names — `cancel`, `isRinging` and the orphan sweep all work off the map, so it is unreachable and will ring. On a windy morning that is a ring Nivaat exists to prevent, so it is a real residual, not a nicety. The only thing that would close it is sweeping AlarmKit alarms the map does not name, and **that is not a drive-by**: the same window makes a just-created alarm look like an orphan to a concurrent isolate, so a careless sweep would cancel live rings and cause the silent mornings this file keeps arguing against. (3) `cancel` and the internal `_cancelEach` drop only what AlarmKit **confirmed** is gone — failure arrives as a `false` return as well as a throw — and `scheduledIds` prunes **per UUID** against what AlarmKit still knows, so an unresolved cancel is a retry rather than a leak. (4) **`isRinging` asks every UUID under the id**, not just the newest: if the refused cancel left the older alarm live and that is what the user can hear, answering "no" lets Nivaat's Rule 1 cancel a ring that is physically sounding. A pre-list build stored one bare UUID per id; `_loadMap` **no longer reads that shape** (no-migration bullet above) and throws on it instead — a test pins that, because the one outcome worth ruling out is reading an old map as "no alarms" and orphaning an armed one in silence.
- **Cross-platform parity is mandatory — every feature must work on BOTH Android and iOS.** Never ship a path that works on one and silently no-ops on the other. When touching anything platform-shaped (notifications, permissions, plugins, `dart:io`, `Platform.is*`), explicitly verify the _other_ platform has a working equivalent — don't assume a plugin handles it. **Burned once (2026-07-13):** we assumed "the `alarm` package requests iOS notification permission" — it does NOT (it only _checks_ `authorizationStatus` and silently drops the notification), so both apps requested permission on Android only and Nivaat's skip cards / Arunoday's bedtime banner would never have appeared on iOS. Fix: both notifiers called `IOSFlutterLocalNotificationsPlugin.requestPermissions` too. (2026-07-20: Arunoday's iOS request was then removed as vestigial — under AlarmKit-only iOS it posts zero notifications, so parity here means *nothing to grant*; Nivaat still requests on both.) iOS permission is a single app-level grant, so requesting from multiple places prompts only once — the "avoid double-prompt" fear was unfounded. Rule: **read the plugin's native source before trusting it to request a permission.**
- **Permission nudges (2026-07-19)**: a denied permission always leaves a persistent home-screen banner with a one-tap fix — `NotificationPermissionBanner` (both apps; Arunoday Android-only, and since 2026-07-20 Arunoday doesn't request the permission on iOS at all — it posts zero iOS notifications under AlarmKit-only iOS), `BackgroundChecksBanner` (Nivaat: Android battery exemption / iOS Background App Refresh), `AlarmPermissionBanner` (iOS AlarmKit). - **Elapsed time is not clock time, and every alarm here means clock time (2026-08-05, REVIEW #10 · #11 · #12 · #13 · #14).** `Duration` counts elapsed seconds; a date and a time of day are calendar values. On a day the zone changes the two stop agreeing, so **`core`'s `calendar.dart` owns both steps** — `calendarDay(from, days)` for "the day after", `clockTimeOn(day, minutesAfterMidnight)` for "22:00 on it" — and every day-stepping or minute-of-day site in both apps goes through them. Five bugs, one shape. `NivaatAlarm.nextOccurrence` walked 24-hour blocks, so on a fall-back day its eight steps covered seven dates and a Sunday-only alarm returned **null** — and null is not "nothing today": `_resolveOccurrence` handing null to `_evaluate` cancels that alarm's ring AND its next check, and since Android checks only ever re-book themselves, recovery needs another alarm's check, iOS's half-hourly refresh, or an app open — so a lone alarm on Android waits for you. Arunoday's bedtime was `midnight + Duration(minutes: bed)`, so a 22:00 bedtime rang at 23:00 in spring and 21:00 in autumn — **re-introduced one line after `_dayAhead` had picked the date correctly**, which is why the day step alone was never the fix. `nextWake`, `setOneTimeExtra`, `_anchorDawn`, the home footer's "tomorrow" and `sleepStartMoment`'s step back all used `+ Duration(days:)` while the resync used calendar days, so **the armed alarm and the countdown disagreed** across a spring-forward night, and `setOneTimeExtra` — which stamps `oneTimeExtraDate` — put "+2h tomorrow" on the wrong morning. `nextDailyBedtime` rolled forward 24h and aimed a 00:15 bedtime at 23:15 the same evening. And `Solar.yearlyDawnExtremes` applied **today's** offset to all 365 days, so the auto bedtime read 22:19 in summer and 21:19 in winter while every daily wake — which goes through `.toLocal()` — stayed correct; it converts each day at its own offset now, and `utcOffsetMinutes` survives only as a **test-only fiction** for machine-independent wall clocks (`solar_test`, `sleep_plan_test` are built on it). **What is deliberately NOT converted:** `dawn + wakeOffsetMinutes`, `base + oneTimeExtraMinutes` and `alarmAt + retryMinutesAfter` are genuinely elapsed — "twenty minutes after first light", "keep checking for thirty minutes" — so leave them alone. **India has no DST, which is the only reason any of this shipped**, and it is also why the tests are shaped the way they are: every assertion in the `dst_test.dart` pair is true in *any* zone ("next Sunday is next Sunday", "22:00 is 22:00") so it stays meaningful under IST, but it only bites where the clocks move — `TZ=America/New_York flutter test test/dst_test.dart`, which is how each fix was revert-proved. **A test that only sees "this week" is soft nine months of the year**, which is why three Arunoday entry points take `now` as a parameter rather than reading the clock — `nextDailyBedtime`, `nextWakeAt` (whose `_firstFuture` walk `setOneTimeExtra` shares, so the countdown and "+2h tomorrow" cannot disagree), and the static `bedtimeWindowAt`, whose **only caller is the arming loop**. Without them a 7-day window opened in August contains no transition, and reverting the fix passes even under that TZ; with them the same revert fails with a bedtime armed at 23:00 and a wake a whole day late. **The two hours a year that have no single answer — the spring-forward hole and the ambiguous fall-back hour — are inherited from Dart, measured and written up on `calendar.dart`; don't restate them here.** **Three older tests fail under that TZ, and they are not one thing:** two are fixtures pinned to an Indian device (`solar_extra_test`'s dawn hour before noon, `controller_test`'s "Tonk ~22:00 zone" bedtime), and the third — `controller_test`'s one-time extra — is a **real latent bug**, traced and filed separately: `_clearExpiredOneTimers` splits `oneTimeExtraDate` back into y/m/d and feeds it to `wakeOn` as a date ARGUMENT, while `setOneTimeExtra` and `wakeOn` both key on the wake INSTANT's local date. Where those differ it evaluates the previous day's wake, finds it past, and wipes the extra inside the same `update()` that set it. All three fail identically at HEAD, so a clean run means those three and nothing else.

**Host-event consume (2026-08-08, reworked 2026-08-09):** core's `HostAlarmEventBridge` + `pendingRing` + `RingDisposition` (a separate axis from wind `CheckOutcome` — never reuse `skippedNoData` for a platform drop). Nivaat settles a held ring on audible / known drop / vanished; Arunoday preserves short host deferrals and skips re-arming preserved ids. The platform's stored time is never Rang proof. Five rules came out of the review and each of them was a real defect first:
  - **Events are delivered at least once, and the claim goes down AFTER the handler.** Claiming first looks safer and loses the event outright: the plugin acknowledges natively as soon as it hands the event over, so a process death between claim and handler leaves it marked done and never applied, with nothing left to redeliver it. Idempotency lives in the handlers (`hostEventKey` matched against history), which is also the only answer available for two isolates — SharedPreferences cannot compare-and-swap.
  - **One failing handler costs its own event and nothing else.** The drain used to copy the queue, clear it, and abort the batch on the first throw — every event beside it gone, with `apply()` still returning normally. Same shape `_sweepOrphanRings` guards each cancel against.
  - **`_settlePending` writes history, rolls on, and clears the pending slot LAST**, because that slot is the only durable record that the occurrence is unfinished. Clearing first left `Missed` in the log with nothing saying tomorrow still needed booking, and on Android nothing else books one. A re-entry finishes what a dead run left, rather than returning early on "already recorded".
  - **Closing an occurrence and rolling on from it are separate acts** (`_hostClosedOccurrences` vs `_hostRolledOccurrences`). Whoever claims `rollOnDone` owns the roll; the other side must check which happened, or the cascade ends up with either two next occurrences or none.
  - **The per-alarm lane tracks a SET of active ids, not one.** With a single slot, alarm B's handler finishing cleared the mark for alarm A, so A's next event queued behind A's own running job — handler waiting on job, job waiting on handler, `evaluateAll` never returning. Two events in one batch was enough.

  **A host settle uses the clock of the pass it runs inside** (`_nowFor`), not `DateTime.now()`. Reaching for the wall clock rolled the cascade past a whole occurrence, and it broke its own test the morning after that test was written.

  **`scheduledAlarms()` is the batch read, and the per-id one is a view over it.** `Alarm.getAlarm(id)` scans the whole list over Pigeon anyway, so asking per id turned one Arunoday resync into twenty-odd platform round trips; the batch also gives a pass one consistent snapshot instead of a series that shifts underneath it. `_cancelExcept` still re-reads immediately before destroying anything — the snapshot can go stale in the gap, and cancelling a `06:00:30` deferral of an alarm whose own minute has passed loses that ring for good.

  **"I could not ask" is never "it is not there".** `scheduledAlarms()` throws when the platform cannot be reached, and an empty map means the platform answered and holds nothing. Returning `{}` on a transient AlarmKit hiccup finalised a morning whose alarm was still armed and about to sound — REVIEW #2's rule pointed at a different call. `scheduledIds()` may still swallow the same failure, because it feeds the orphan sweep, where cancelling nothing is safe.

  **A settle owns a slot by OCCURRENCE, never by plugin id.** Ring ids repeat daily (`block + alarmId`), so last Tuesday's lateRing wears tomorrow's number, and accepting that as ownership let an old event clear a pending ring that was still owed.

  **"Already settled" means any row for that occurrence carrying a `ringDisposition`** — not just a missed one. Only the settle path writes that field, so its presence means some run reached a verdict; testing only for missed/unknown made a crash between the row and the clear write a SECOND verdict beside the first (`Couldn't confirm` under a real `Rang`). A premature `Rang` from the pre-hold era carries no disposition, so supersession can still find it.

  **A failed handler retries on the NEXT barrier, not three times inside one drain.** Three attempts in the same millisecond, against the conditions that just failed, is a busy loop wearing a retry policy's clothes; a transient fault needs the next evaluate pass.

  **A pre-T arm saves its CheckState immediately**, and a post-T arm saves its pending on the same turn. A drop landing in the gap otherwise matched nothing at all — `state` was still only in memory — and a morning that never rang was recorded as merely unconfirmed instead of missed.

  **`_stillLive` re-reads `enabled` as well as existence.** A toggle-off is the delete race by a quieter door, and the orphan sweep cannot catch it, because a disabled alarm has not left the store.

  **Arunoday only treats a later plugin time as a host deferral once the alarm's own moment has arrived.** The host defers a ring because it tried to fire and was refused, so before that instant there is nothing to have deferred — without the clock test, nudging wake 06:00 → 05:59 the night before read as a 60-second deferral and the edit silently did nothing.

  **The same three rules, applied everywhere rather than where they were first spotted.** Each of these was fixed once at the site a reviewer named and left standing at its sibling, which is how the next review found it again:
  - *A failed query is never a negative answer* — `isRinging` throws now too, and that one matters more than `scheduledAlarms`, because every caller of it is asking permission to DESTROY something: `_cancelExcept` and the orphan sweep both read `false` as "safe to cancel", so a swallowed AlarmKit error silenced an alarm that was physically sounding.
  - *Cross-isolate state reloads before every read and write* — `CheckState` as well as history and the pending ring. It carries `ringScheduled`, so a foreground holding a launch snapshot re-saved an old one over a background isolate that had just cleared it.
  - *Ownership is by occurrence, never by a daily-reused id* — in `_recoverAmbiguousPending` as well as `_settlePending`. Tomorrow's pre-arm under the same number made today's stale pending look armed, so it was never finalised; recovery now compares the scheduled TIME too.

  **`rollOnDone` is written AFTER the roll, in both places that roll.** Marking first prevents a double roll and buys it with the worse failure: die in the gap and recovery reads "already rolled", so the occurrence closes with nothing after it and — on Android, where checks only re-book themselves — the alarm waits for a manual app open. Rolling first risks re-arming the same ring for the same instant, which is a no-op. `_settlePending` and the post-T hold must agree on this or one of them is wrong.

  **`_settlePending` re-reads the pending slot after the roll**, rather than trusting the `ownsSlot` it computed before it. The roll is a whole evaluation — fetch, arm, state write — and it is exactly where the NEXT occurrence's pending gets written; clearing on the older answer deleted a ring that had just been armed.

  **The morning's card comes down on every exit from the post-T hold**, not just the straight-through one. A drop settling mid-await used to return past that line and leave `Still checking` in the shade for a ring already recorded as missed.

  **`_stillLive` compares every field that decides WHAT gets armed** — time, weekdays, court, limits, retry cap, enabled — not just existence. An edit is the delete race with the alarm still present: the snapshot says 06:00, the store says 07:00, and `next` came from the snapshot, so the pass arms a ring for a time the user has moved away from, on a locker the new occurrence never looks at. Consequence for tests, same as REVIEW #23's: **an alarm the store has never heard of is a fixture production cannot produce**, so a test evaluating a variant must seed it.

  **`unknown` is the only verdict a later one may replace, and only by `missed`.** `Couldn't confirm` does not mean "we decided nothing happened" — it means *we never found out*, so a known `AlarmDropped` arriving afterwards is not a competing opinion, it is the answer. Every other pair is a downgrade or a duplicate: nothing replaces `missed`, and **nothing replaces `rang`** — a late drop after the user has already stopped an audible alarm must not rewrite the morning they woke up to. `_canReplaceVerdict` is the whole rule and both directions are tested. **Residual, accepted:** once the pending slot is cleared the occurrence is closed, so a drop arriving after that has nothing to attach to and the row stays `Couldn't confirm`. Reachable only if the drop is recorded natively between our last drain and the `scheduledAlarms()` read; the cost is a vaguer word for a morning that is correctly recorded as not having rung, and closing it would mean re-opening settled occurrences out of history alone.

  **The two platforms fail a re-arm in OPPOSITE directions, and `engine_fakes` must model both.** Android's `Alarm.set` stops the same id before scheduling, so a refusal leaves the locker empty; AlarmKit schedules first and cancels afterwards, so a refused create leaves the OLD alarm armed (REVIEW #5, deliberate). `FakeRing.destructiveOnFailure` carries the difference — it was hard-coded to Android's answer, with a comment asserting AlarmKit "cancels then schedules", which is backwards. That left the iOS direction untested, and the thing it hides is a ring the engine has stopped tracking: `host_event_test` now pins the invariant that a windy morning still cancels it.

  **One id can hold more than one live alarm, and `ScheduledAlarmInfo.handles` is how a caller finds out.** `dateTime` describes only the newest AlarmKit UUID, so Arunoday's preserve check — "this id is already correct, leave it alone" — read a straggler at the old minute as nothing at all. That matters because `scheduleRing` is the ONLY thing that ever retries a cancel AlarmKit refused: preserving skips it, so the documented "duplicate alert you can stop" quietly becomes permanent and the 06:00 the user edited away from keeps ringing. `handles != 1` now forces a re-arm.

  **AlarmKit pruning lives in `_livingMap`, not in one caller.** It used to sit inside `scheduledIds`, which was fine while that was the only batch read — then `scheduledAlarms` arrived, Arunoday moved onto it, and Arunoday stopped pruning dead UUIDs entirely. Behaviour attached to a call site stops applying the moment a second call site appears.

  **"Not yet" is not "handled" — and a handler that wants a retry must throw an `Exception`, never an `Error`.** `HostAlarmEventNotReady` is the signal; the bridge defers on `Exception` only, so an `Error` is lost rather than retried. Nivaat throws it when a drop arrives with no pending and no saved `ringScheduled` to attach to, which closes the last window between arming a ring and recording it (one microtask as `scheduleRing`'s future completes — and a refused foreground service lands in exactly those seconds, upstream #424). An event that genuinely never matches costs three bounded attempts and a log line.

  **A move is deferred on the same terms as a drop, and neither pending save may clobber one.** Scoping the retry to drops alone was an unjustified narrowing: a deferral claimed with nothing to write it onto leaves `scheduledFor` at the time the host has already moved away from, and everything downstream keys on that — `_recoverAmbiguousPending` reads a ring the platform still holds as a DIFFERENT ring and settles the morning as vanished, and a second move falls outside `_hostEventSlack` as the wrong occurrence. **And the deeper half was not the retry at all:** the handler usually *does* match (synthesising from CheckState), records the new time, and then the arming pass's own `savePendingRing` puts its stale request straight back on top. Both saves go through `_savePendingKeepingHostMove` now — fixing only the later of the two left the earlier one still clobbering, which is how a test written for this passed against unfixed code twice.

  **The pending slot belongs to ONE occurrence, and the move write has to say so too.** `savePendingRing` keys on `alarmId` alone and `_matchPendingForHostEvent` will synthesize a pending for a different morning, so a deferral of tomorrow's `nextRing` wrote over today's held ring and erased the only record it was still owed. The settle path's clear already followed this rule; the move write did not. Declining costs a deferral we cannot store for an occurrence that does not hold the slot — recoverable, since the roll-on arms it fresh — whereas losing the held pending is not. **And a deferral only ever moves a ring FORWARD**, so an event naming an earlier time than the one held is a replay of a move already superseded; applying it rolled `06:01:00` back to `06:00:30`.

  **Any host-event test about a MOVE must be dated on the live clock.** A move about a ring whose time has passed is correctly ignored as a stale replay, and `_nowFor` falls back to the wall clock outside an evaluate lane — so a fixture-dated move test exercises the rejection path and passes whether or not the rule under test exists. `armLiveAtT()` in `host_event_test` is the shared fixture; two tests written against 2026-08-08 passed against deliberately broken code before this was understood.

  **A mid-pass injection test must DRAIN inside the call, not just queue.** `_EmitsDuringSchedule` awaits `emitHostEvent` from within `scheduleRing`, so the handler provably runs before the pass records the ring. Queueing alone raced — the pending was usually saved first — and the test passed with and without the fix. It also has to be dated on the LIVE clock with seconds stripped: a fixture-dated ring is correctly ignored as a stale replay, and a time carrying seconds makes `nextOccurrence` roll to tomorrow so the pass becomes a pre-arm, which owes nothing and writes no pending.

  **The same retry cannot help Arunoday, and pretending otherwise made things worse.** A version of this threw `StateError` from its handler — an `Error`, so nothing deferred and the event was lost harder than before; the `_armRunning` branch returned normally anyway; and structurally **every one of Arunoday's barriers is inside `_arm` itself**, so a deferred event is re-run during the very pass that would retry it and burns its attempts while `_armRunning` is true. Arunoday's handler is **advisory on purpose**: it never reads the event, `_arm` is a complete idempotent rebuild, and app resume / a settings change / a ring ending all run the same rebuild. A failed pass costs promptness, not correctness. That stops being true the moment the handler starts acting on `event` itself.

  **A programming `Error` in a handler comes out of `apply()`.** Errors are deliberately not caught (policy: Exceptions soft-fail, Errors are bugs and stay loud), but the drain runs in a detached microtask — so "loud" meant an unhandled zone error while `apply()` returned success with the batch eaten. It is captured and rethrown through the barrier the caller awaits.

  **Every platform read that a decision hangs on happens inside the lane that decides.** `_recoverAmbiguousPending` took one `scheduledAlarms()` snapshot for the whole sweep, then settled each pending against it — but the drain, the other alarms' settles and their roll-ons all sit in between and can arm or move that very id, so an older snapshot called a live ring vanished.

  **Both apps register the host-event handler BEFORE the plugin is initialised**, because `Alarm.init()` replays everything the host recorded while no engine was running. Nivaat gets this from `NivaatEngine`'s constructor; Arunoday's `main` builds the controller first, and the handler additionally waits for `loaded` — an event arriving with settings unread reaches the no-location branch, which cancels every alarm there is.
