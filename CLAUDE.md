# weather-aware-alarm-apps monorepo

Two Flutter alarm apps sharing one core package. **Read SPEC.md before changing any behavior — every product decision there is locked with Samyak; don't silently re-decide.**

## Layout

- `packages/core` — pure logic: solar math, sleep plan, wind engine, Open-Meteo client, theme, models, repos. **All business logic lives here, fully unit-tested.** Apps stay thin.
- `apps/arunoday` — dawn alarm app (daily driver, priority app).
- `apps/nivaat` — wind-conditional badminton alarm.

## Conventions

- UI: pure black `#000000` scaffolds / app bars, dark-only, minimal. Accents: Arunoday `AppPalette.dawn`, Nivaat `AppPalette.wind`. Elevated overlays (sheets / dialogs / snackbars / `DropdownButton` menus / `showTimePicker`) use `AppPalette.surface` (`#0E0E0E`) — menus via theme `canvasColor`; time picker via `timePickerTheme` + pinned `ColorScheme.surfaceContainer*` (ignores `dialogTheme`); `surfaceTint` off (2026-07-23). No third-party UI kits.
- **Design pass (2026-07-20, Samyak's premium-feel round)**: (1) hero type — ships THIN (the original look); the Settings toggle "Bold clocks & titles" (`Appearance.heavyType`, persisted, default OFF) switches `buildOledTheme(heavyType:)` to w700/w600 heroes with tabular figures; body/labels stay w400 in BOTH modes (the weight contrast IS the look — don't bolden the quiet styles; locked by `design_test.dart`). Each app's `MaterialApp` rebuilds live via `ValueListenableBuilder` on `Appearance.heavyType`. (2) `CraftedBy` (core) renders `CRAFTED WITH ♥ BY SAMYAK` at the foot of BOTH home screens — the heart is `Icons.favorite` (NOT a text glyph: Android font fallback promotes text hearts to the baked-red emoji — device-caught), tapping SAMYAK opens `craftedBySiteUrl`. (3) All motion runs 50% slower: `applyMotionPacing()` (core `motion.dart`, `kMotionSlowdown = 1.5` via `timeDilation` — verified release-safe in Flutter source, it's a plain runtime scale) called at the top of both mains; experiment, revert = delete those two calls. Both Info.plists already had `CADisableMinimumFrameDurationOnPhone` for 120Hz ProMotion. (4) **Launch screens are black** on both OSes (Android `launch_background*.xml` + `Theme.Black` styles, iOS storyboard bg) — never reintroduce the template white. (5) **Portrait-only (2026-07-22)**: landscape overflows home/sheets/dialogs — lock via Android `screenOrientation="portrait"`, iOS Info.plist portrait-only (phone + iPad) + `UIRequiresFullScreen`, and `lockToPortrait()` in both mains; don't re-enable landscape without a layout pass.
- **Nivaat navigation (2026-07-20)**: the home top bar has ONE entry point — the settings (tune) icon; courts, alarm sound, and history are settings tiles (that order), and home shows a live `Still checking wind · until HH:MM` cue (tap → history) only while a per-alarm retry window is open (2026-07-22 — replaced the permanent last-outcome dump; cap is 1/30/60 min per alarm since 2026-07-26). Enabled home rows (+ alarm editor under the clock) show sentence-case `in {Xh Ym}`, or `in {Nd HHh}` past a day (wall-clock :00 ticks, re-aimed on resume — never `Timer.periodic`, which drifts by however long the app was suspended; not Arunoday ALL-CAPS; hidden during that alarm's post-T retry — editor still counts down to the draft clock mid-window / when switched off: picker feedback). **One card per morning (2026-07-26)**: a single notification (`NivaatIds.card`, the old 40000 heads-up block) posts at T as `Still checking` and is REWRITTEN in place to `Skipped` / `Cancelled` — there is no second card, and the old 50000 skip block is gone (nothing sat above it, so no renumbering; an upgrade can orphan one previously-posted skip card, which is a dev-only concern with no installed base). Every push **alerts** — no quiet variant, no per-platform presentation flags. Cancelled only by a late ring (the ring becomes the card), delete, or court-gone; a toggle-off or abandoning edit rewrites it to `Cancelled` instead, since the alarm still exists. Mid-window **continue** edits (limit, Keep checking, add-only weekdays) keep today flying; a Keep-checking change re-posts the card with the new deadline built from the STORED reading — never rebuilt from the edited alarm, which put new limits beside the old numbers ("Too windy · wind 5 (≤20)"). **`retainInFlightEdits` must check BOTH windows (2026-07-31):** the old one (widening after death must not resurrect a morning) *and* the new one — shrinking 30→1 at T+2 checked only the old, so it re-posted an ALERTING card promising `watching until 06:01` at 06:02 plus an immutable row to match, the exact broken promise the one-card model exists to prevent. Both dead-window paths now go straight to `_finaliseDeadWindow`; `morning_story_test` 14d locks it, including the general rule that no row may promise a deadline already past when it was written. Don't re-add top-bar icons. Arunoday's settings rows are grouped by ritual: wake pair, bedtime group, shared sound, then APPEARANCE, then LOCATIONS. Both settings pages scroll as ONE surface (2026-07-20) through core's `FlashingScrollbar` (the flash-on-open-if-overflowing cue) — no inner scroll regions. **Nivaat home alarm list** also uses `FlashingScrollbar` (2026-07-22). **Nivaat unique HH:MM** (2026-07-22): no two alarms share the same clock minute (court/weekdays ignored; ±1 min for multi-court); N18 inline + `upsertAlarm` returns `false` on conflict.
- **App icons (shipped 2026-07-20, switchable)**: all three candidates per app ship; Settings picker drives core's `app_icon.dart` over the `core/app_icon` MethodChannel (ids "1"/"2"/"3"; defaults Horizon/Shuttle). The picker ring updates optimistically — iOS runs the set-icon completion only after its system alert is dismissed — and reverts if the platform refuses. Sources: `branding/` + `tools/make_icons.py` (numpy SDF renderer); `--apply` rewrites the real launcher assets (Android adaptive mipmaps, iOS appiconsets, Settings thumbnails) — never hand-edit those PNGs. Android: MainActivity keeps the MAIN/LAUNCHER intent-filter + default icon (moving it onto aliases breaks `flutter run` after a clean — the tool's pre-build manifest parse only reads real `<activity>` tags); `.IconTwo`/`.IconThree` aliases (manifest-disabled) carry the alternates; switching flips component-enabled states with `DONT_KILL_APP`, safe because the `alarm` + `flutter_local_notifications` plugins resolve entry points via `getLaunchIntentForPackage` (verified in their sources). **Android closes the app on every switch and that is not fixable here (2026-08-01)**: the component being disabled is always the one the running task was launched through, so Android tears the task down — `DONT_KILL_APP` spares the *process*, not the activity, and the intent-filter can't move off `MainActivity` (above). So the picker **says so first on Android** (X7's `CHANGE APP ICON` notice, `appIconRestartWarning`); unannounced the close reads as a crash. It **informs rather than asks** — one `OK`, no Cancel — which makes the dismissible barrier the only way out and therefore load-bearing, and its paddings are pinned tighter than M3's (locked by `design_test`). `MainActivity` then **closes the app itself** (`finishAndRemoveTask()` after a successful `setIcon`, both apps, keep in sync): Android would anyway, but the beat it took read as a freeze. `setIcon` also skips disabling entries already off — only one is ever on and each redundant call is a binder round-trip the user waits through; still a loop, so corrupt two-on state resolves. **iOS must never get that dialog**: `setAlternateIconName` keeps the app running and the OS shows its own alert, so ours would be one more thing to dismiss. The platform split uses `defaultTargetPlatform` (not `Platform.isAndroid`) precisely so both branches are testable on the host. iOS: `AppIconTwo`/`AppIconThree` appiconsets + `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES` in every build config; the OS confirms switches with its own alert.
- Alarm scheduling goes through `core`'s `AlarmScheduler` interface, chosen by `createAlarmScheduler`: **`AlarmKitScheduler` on iOS (min target 26.0)**, `AlarmPkgScheduler` on Android. **iOS is AlarmKit-only — there is NO `alarm`-package fallback** (2026-07-18): if the user denies AlarmKit, `scheduleRing` silently no-ops (`PlatformException` caught) and `AlarmPermissionBanner` (shown on both home screens, driven by `alarmSchedulingDenied()`) nudges them to Settings via `url_launcher` (`app-settings:`). So `AlarmPkgScheduler` is effectively Android-only (`warningNotificationOnKill: false` — Android's ring genuinely survives kill). **Both wake and bedtime rings use AlarmKit on iOS** (2026-07-16: a real system alarm that survives force-quit/reboot beats the `alarm` package's in-process Timer; cost — Arunoday's bedtime "+1h" ritual is **Android-only**, since AlarmKit alerts are Stop-only). Never call the `alarm` package directly from screens, except ring-screen `Alarm.ringing` listeners. (AlarmKit's auth prompt is simulator-verified; real-device iOS ring behavior is still untested.)
- **Scheduler / notification id blocks — don't "tidy" them smaller (2026-07-26)**: every id is `block + index`, decodable by division (`id ~/ width` = which namespace, `id % width` = which alarm/slot). **Rule: the block width must exceed the largest index it can ever hold, with room to grow.** Arunoday: 1000-wide blocks over `ArunodayIds.slots` day-slots (1000 wake, 2000 bedtime, 3000 bedtime-again; `isBedtimeAlarm` = 2000..3000), each keyed on the alarm's **calendar day** so a given day's alarm keeps one id no matter when the resync runs. Nivaat: 10000-wide blocks over alarm ids (10000 ring, 20000 late ring, 30000 wind check, 40000 the morning's card). The 50000 skip block was **removed** with the one-card model (2026-07-26) — nothing sat above it, so nothing renumbered. Both maps live in one file per app (`lib/src/ids.dart`) with an `ids_test.dart` that asserts no two ids ever collide — add new numbers there, never inline. **Nivaat's two ring lockers are split by ROLE — the pre-arm for an occurrence's own time vs a LATE ring armed after T.** An alarm has two live rings whenever a retry inside the post-T window finds calm air: the same pass then closes that occurrence and pre-arms the next, and with one locker that pre-arm cancelled the late ring ~10s before it sounded while history still logged "Rang". Three rules come with the split: arming a late ring must `cancel` the pre-arm it supersedes (else the alarm sounds twice seconds apart); a skip must cancel **only** the pre-arm locker (clearing the late locker would re-create the bug); and Rule 1 must both test `isRinging` on both lockers *and* gate its "rang" row on `!t.isBefore(stored.alarmAt)`, or a resync during a late ring logs *tomorrow* as rang. **Do not "simplify" this to day-parity** — it looks equivalent and silently fails whenever consecutive occurrences are an even number of days apart (a Mon+Fri alarm is 4 days, same parity, collision returns). **Why not compact these to 10/20/30:** with a 10-wide block, bumping `windowDays` 7→14 puts wake id `10+13 = 23` inside the bedtime block, so `isBedtimeAlarm(23)` turns true for a WAKE alarm and the ring screen offers "+1h not sleepy" at dawn — a silent break from a one-line change that looks safe. The blocks cost nothing: these ids are ephemeral (recomputed every resync, never persisted as user data). **And two offsets are load-bearing, not cosmetic:** the `alarm` package posts its ring notification with `startForeground(id, …)` — i.e. **its Android notification id IS the alarm id** — so a skip/heads-up card sharing that number would erase the ring's own card and Stop button. Verified in the plugin's Kotlin (`AlarmService.kt`), not inferred.
- **Cross-platform parity is mandatory — every feature must work on BOTH Android and iOS.** Never ship a path that works on one and silently no-ops on the other. When touching anything platform-shaped (notifications, permissions, plugins, `dart:io`, `Platform.is*`), explicitly verify the _other_ platform has a working equivalent — don't assume a plugin handles it. **Burned once (2026-07-13):** we assumed "the `alarm` package requests iOS notification permission" — it does NOT (it only _checks_ `authorizationStatus` and silently drops the notification), so both apps requested permission on Android only and Nivaat's skip cards / Arunoday's bedtime banner would never have appeared on iOS. Fix: both notifiers called `IOSFlutterLocalNotificationsPlugin.requestPermissions` too. (2026-07-20: Arunoday's iOS request was then removed as vestigial — under AlarmKit-only iOS it posts zero notifications, so parity here means *nothing to grant*; Nivaat still requests on both.) iOS permission is a single app-level grant, so requesting from multiple places prompts only once — the "avoid double-prompt" fear was unfounded. Rule: **read the plugin's native source before trusting it to request a permission.**
- **Permission nudges (2026-07-19)**: a denied permission always leaves a persistent home-screen banner with a one-tap fix — `NotificationPermissionBanner` (both apps; Arunoday Android-only, and since 2026-07-20 Arunoday doesn't request the permission on iOS at all — it posts zero iOS notifications under AlarmKit-only iOS), `BackgroundChecksBanner` (Nivaat: Android battery exemption / iOS Background App Refresh), `AlarmPermissionBanner` (iOS AlarmKit). All render through core's `NudgeBanner` shell and re-check on app resume. No banner ever flashes behind its own first-run dialog: the notification banners gate on a per-app "asked" flag + `recheckAfter` (the startup request future), the battery banner on `batteryAskInFlight` (set around the once-ask, cleared by the resume that answers it). **Armed-home only (2026-07-22)**: both apps hide these on the empty intro (Nivaat: no alarms; Arunoday: no location) so the hero stays clean — they appear once there's something to protect. **Gating differs by kind, on purpose**: X2/X3 are permissions, so they gate on "the prompt was ANSWERED no" (`alarmSchedulingDenied` is true only for AlarmKit `denied`, never `notDetermined`; the notification banners keep a per-app "asked" flag) — N16 is not a permission but a live OS setting Android will re-ask forever, so it reads the setting and suppresses itself while its own once-ask dialog is up. One rule three ways: never appear behind the dialog you are about to show. **Arunoday's X3 text lost its "and bedtime reminders can't appear" clause (2026-07-31)** — the bedtime is an alarm, not a reminder; it still rings with notifications off, which the "sound only, no Stop" clause already covers, and Arunoday posts no other notification. **Both empty intros sit a third down** (1:2 spacer rhythm, A9 and N14) — Nivaat's was centred and landed at 46% against Arunoday's 28%; each app's message test asserts the bound, since neither can see the other.
- **Nivaat history (2026-07-19, append-only pushes since 2026-07-26)**: every card push appends exactly ONE row and **nothing is ever rewritten** — a row says what was true when written. Three kinds (`HistoryKind`): `stillChecking` (carries `watchedUntil`, the promise that push made), `outcome` (carries `checkingEndedAt`, which only shows as `· watched until` when checking outlasted the last reading — the network-blip-at-the-cap case), and `cancelled` (bare line **and** a bare sub — no `last checked` either, unlike every other row; a cancelled row only ever exists directly beside the still-checking row that already carries the reason, the numbers and the reading, while the cancelled *card* repeats all three because it has no neighbour — locked, don't "restore" the freshness clause). The reason (windy/gusty/no-data/rang) is a SEPARATE axis from the kind, because a morning's still-checking and outcome rows share a reason but render different lines. **The log is uncapped (2026-07-31)** — `NivaatStore` used to keep only the newest 60 rows, which contradicted SPEC's "permanent" and, at a row per card push, amounted to about a fortnight for two alarms; deleting a court is now the only thing that removes rows. Don't re-add a ceiling: if the JSON blob ever gets heavy, the answer is a real database, not a smaller window. Rows are keyed `alarmId + at + pushSeq`, a counter kept per occurrence in `CheckState` (whose `cardShown` flag — renamed from `extendedCheckShown`, which pointed at a deleted method — gates whether a morning has anything to explain): two isolates racing on one push read the same number and converge, two real pushes both survive. Content can't be the key — Keep checking 30→60→30 leaves two byte-identical rows that must both stay. `nivaatLatestRowPerOccurrence` breaks a pushSeq tie by list order (callers pass newest-first) — every row written before push numbers existed carries 0, so number-only comparison read a finished old morning as an open window. Adjacent rows carry what annotations used to (`watchStoppedAt`, the `watchedUntil` rewrite, `copyWith`, `· failed` and the whole `watched to X of Y` vocabulary are all GONE): a promise of 06:30 above `last checked 06:10` **is** the shortfall. `last checked` everywhere except the ring card's plain `checked`. Both the line and the sub are built outside the widget (`nivaatHistoryLine` / `nivaatHistorySub`) — a string built inside a widget is an untested string, and the sheet was caught still saying `checked` because a test rebuilt the sub by hand. Every write goes through `NivaatEngine._pushCard`, which stamps the row and pushes the card together, row first (a failed notify leaves history complete; the reverse would leave a card with nothing behind it). Abandon paths (toggle / kill-edit / delete → `engine.abandonOccurrence`) finalise a fired ring first; continue-edits use `retainInFlightEdits`. Finalisation rolls straight into the next occurrence. Foreground resyncs call `NivaatStore.refresh()` first — per-isolate caching otherwise hides background writes until a cold start. **UI freshness (2026-07-22)**: background checks ping the UI isolate after `evaluateAll` (`pingNivaatUiResync`); home also resyncs on app resume. **`resync` no-ops until `loaded` (2026-07-23)** — pre-init courts are `[]`, so orphan prune would wipe the whole log.
- **Nivaat's two wake tolerances are derived, not chosen (2026-07-26)**: `kNivaatWakeGrace` is **zero** — both OSes fire at or after the requested instant, never before, so there is nothing to forgive; a backwards clock nudge just books another check for T. `nivaatOccurrenceEndsAfter` runs to the end of the **cap's minute** — history prints HH:MM, so anything before 06:31 displays as `06:30` and is honest. They must stay separate: widening the first to absorb late wakes would make a T−1m check count as T and post "still checking" before the alarm was due. The old shared 5s meant a cap wake 10s late was a new morning, so the engine closed the books on the previous reading and never checked again — `last checked 06:29` on a 30-minute window, `06:00` on a 1-minute one (device-caught).
- Times: all solar math is UTC-internal, converted at the edge. Location = saved lat/lon, never GPS.
- **Whole minutes only in the app layer**: `core` computes dawn/sunrise to the second, but the apps floor them to the minute at the controller boundary (`dawnOn`/`sunriseOn`). Dawn's seconds drift ~±25s/day; letting them into wake times makes every derived display (picker anchors, ring moments, sleep math) flicker by one minute. Never quote a second-precise time to the user.
- Tests: `packages/core/test` validates against real-world reference numbers recorded in SPEC.md (Jaipur/Tonk/BLR dawn times, ring-rate expectations). Keep them passing; they are the spec-as-code.

- **MESSAGES.md is the string spec, and it is now enforced (2026-07-26).** Every user-facing string in either app lives there under an ID, and **every one is asserted by a test**: `message_test` (arunoday) · `notification_message_test` + `screen_message_test` + `morning_story_test` (nivaat) · `shared_message_test` (core). Anything with a branch is a pure builder (`apps/arunoday/lib/src/messages.dart`, Nivaat's `engine.dart` / `skip_notifier.dart` / `courts_sheet.dart`, core's `alarmsOffMessage`) asserted directly on **every** branch; flat labels are asserted by rendering the real widget. When a template has a branch, check the branch can happen before writing it down. **The same drift hits dartdoc: when you change a body, re-read the sentence above it.** Three landed in one session (2026-07-31) — `HistoryRecord`'s "append-only for events" after rows became immutable, `_pushCard` summarised as card→row while doing row→card, and `retainInFlightEdits` still promising "finalisation on the next evaluate" after it began finalising on Save. Every time the body was correct and the summary described the design it replaced, and twice the stale summary described something actively unsafe to restore. **The place-picker refusals are builders now too (2026-07-31)** — `ArunodayController.placeRefusal` (A16 polar + same-dawn) and `NivaatController.courtRefusal` (N21 same-area). Add place validation to the controller, never to a picker call site. **N3's channel constants are `@visibleForTesting` public** for the same reason plus a harder one: `SkipNotifier.channelId` is **persisted by Android**, which freezes a channel's importance at creation — rename it and you orphan the live channel and silently reset the user's sound choice, so it is locked by a test.
- **Stopping a ring puts the app back where it was (2026-08-02):** the full screen intent opens the app just to show `RingScreen`, so unless the user had ALREADY opened it themselves, `RingGate` calls core's `sendAppToBackground()` (`core/app_window` → `moveTaskToBack(true)`, in BOTH MainActivities — keep in sync) as the ringing set empties. Every exit routes through there: in-app STOP, the notification's Stop, and the swipe the plugin treats as Stop. **Ownership is decided ONCE, at ring start** (`alarmOpenedTheApp`, `kRingForegroundGrace` — the why is in their dartdocs, don't restate it here) and the hide runs BEFORE `onRingingChanged`, so no callback can cost the user their screen. Hide, don't `finish`: the task survives, so reopening is warm and a still-ringing alarm keeps its notification. **Every `core/*` channel must be answered by BOTH MainActivities**, which `channel_parity_test` (Arunoday, reads both) enforces as a whole map — channel keys by equality so a handler core no longer calls fails as dead Kotlin, methods per channel by subset since an unused branch is only waste. Both halves fail SILENTLY otherwise: core swallows `MissingPluginException` so a ring can't die on a missing handler, and an unhandled method falls through to `notImplemented()` into the same place. **iOS needs none of it and gets none** — AlarmKit never opens the app, and Apple ships no self-background API, so the split uses `defaultTargetPlatform` and stays host-testable (`app_window_test`).

## Build notes (hard-won, don't rediscover)

- JDK: brew formula openjdk@21, wired via `flutter config --jdk-dir`. Android SDK: `~/Library/Android/sdk` (headless, no Android Studio); use the SDK's own `cmdline-tools/latest/bin/avdmanager` (the brew one points at the wrong root).
- Both apps force `compileSdk = 36` AND carry a root-gradle reflection override forcing plugin modules to 36 (the `alarm` plugin pins 34 but its `flutter_fgbg` dep needs 35+).
- Nivaat Android needs core-library desugaring (flutter_local_notifications).
- **Nivaat release R8 (2026-07-20):** Flutter enables minify/shrink on release APKs. Without `apps/nivaat/android/app/proguard-rules.pro`, R8 horizontally merged `android_alarm_manager_plus`'s `FlutterBackgroundExecutor` into `androidx.lifecycle.ServiceLifecycleDispatcher` → release APK “Nivaat keeps stopping” on first tap (`AndroidAlarmManager.initialize()` in `main` before `runApp`). Debug builds don't minify, so `flutter run` never caught it; Arunoday is unaffected (no that plugin). `AndroidCheckScheduler.initialize` also soft-fails so a future native glitch can't brick launch. **`AndroidAlarmManager.initialize()` is deferred to after the first frame** (still before cascade booking) so its background FlutterEngine can't race the main engine during cold start. **Also keep `androidx.work.**` + Room** — Nivaat alone pulls `workmanager`; R8 stripping `WorkDatabase_Impl` killed release installs at `InitializationProvider` before Flutter ran (`NoSuchMethodException`), while `flutter run` debug looked fine. After editing those keep rules: `flutter build apk --release` and check mapping still has `FlutterBackgroundExecutor -> FlutterBackgroundExecutor` and `WorkDatabase_Impl`.
- **Notification small icon + the resource shrinker (2026-08-01):** Android draws a small icon as an **alpha mask** — only the alpha channel survives — so `@mipmap/ic_launcher` rendered as a featureless **white blob, identical in both apps**. Each app now ships its own monochrome silhouette on transparent ground at `res/drawable/ic_notification.xml` (a vector, hand-authored; `tools/make_icons.py` draws full-colour launcher art, a different problem). `AndroidInitializationSettings` and the `alarm` plugin's `NotificationSettings(icon:)` both point at it via core's `kNotificationIconRes` — **the name is compiled into core, so both apps must ship that exact drawable**; each app's `notification_icon_test` reads it and `keep.xml` off disk, since nothing in Dart connects either to the string. **The trap:** the name only exists as a runtime string, so R8's *resource* shrinker deleted the drawable (`resources.txt`: `is not reachable`) and debug builds don't shrink, so `flutter run` looked perfect. The two consumers then fail differently — the `alarm` plugin's `getIdentifier` falls back to the launcher icon (blob returns, silently), `flutter_local_notifications` rejects `initialize` with `invalid_icon`. Fixed by `res/raw/keep.xml` (`tools:keep`); **keep its comments free of `--`**, R8 parses it as XML. Verify a build with `aapt2 dump resources <apk> | grep drawable/ic_notification` (expect `reachable from keep xml file` in `resources.txt`), and for the shape itself `aapt2 dump xmltree <apk> --file res/<name>.xml` — the `pathData` must match source. **Render before shipping an icon change:** `python3 tools/preview_notif_icons.py` parses the real drawables and draws them at 18/24/72px; both first drafts were wrong in ways invisible in XML and obvious at 18px. iOS has no counterpart — it shows the app icon, and Arunoday posts no iOS notifications at all.
- **Ringing over the lock screen — most of it is the plugin's call, not ours (2026-08-02):** the `alarm` package posts its ring with a full screen intent, but Android decides whether that takes over the screen — "While the user is using the device, the system UI might display a heads-up notification instead of launching your full-screen intent" (developer.android.com, *Create time-sensitive notifications*). **So "always full screen" is not achievable on Android**; when the app is already open the takeover is `RingGate`'s anyway, not the OS's. For the *locked* case the plugin's `notificationObserver` (`AlarmPlugin.kt`) **already** calls `setShowWhenLocked(true)` + `setTurnScreenOn(true)` when a ring starts and reverts both when it ends — that is why the ring screen reaches the keyguard, why the app vanishes back behind it on STOP, and why **neither manifest may declare `android:showWhenLocked` or `android:turnScreenOn` itself**. **That was tried and reverted the same day (2026-08-02), and the reason is a security one:** a manifest attribute applies to *any* launch while the lockscreen is up, not just rings, so tapping a notification on the lock screen opened the whole app with **no PIN** — device-confirmed. The plugin's runtime call is the correctly scoped version of the same thing, it is on only while a ring sounds, and adding the attributes measurably changed nothing on a warm device. The only thing they bought was the cold start — the platform's own `attrs_manifest.xml` says an activity "will be transitioned to the stopped state if it is started while the lockscreen is up" without the attribute, and the plugin's lifecycle-aware LiveData cannot reach an activity already in that state; that is not worth a standing hole, and the plugin's own `INSTALL-ANDROID.md` has called the block unnecessary since 5.0.0. `ring_manifest_test` now **forbids** both attributes anywhere in either manifest (aliases inherit unset ones from their target, so the check is manifest-wide) and still requires `USE_FULL_SCREEN_INTENT`. Never use `FLAG_SHOW_WHEN_LOCKED`/`FLAG_TURN_SCREEN_ON` either. **The fingerprint prompt on top of the ring screen is that same observer**, which then calls `requestDismissKeyguard` — on a secure keyguard that means "authenticate", not "show over" (upstream issue #412, fix proposed in PR #415). **And swiping the ring notification away stops the alarm on purpose:** `NotificationService.kt` gives the notification a delete intent that IS the Stop button's `stopPendingIntent` (shipped in 5.0.3, "Added alarm stop on notification dismiss"), so swipe and Stop are indistinguishable in Dart and `NotificationSettings` exposes no knob. The first of the three is Android's and nothing fixes it; the other two are the plugin's, and only a fork fixes them locally — **this repo has never forked or overridden a dependency** (every third-party entry is a plain pub.dev version; the one `path:` dep is our own `core`) and didn't start here, so both went upstream instead — the swipe as issue #413 plus PR #414, the keyguard prompt as PR #415 against someone else's issue #412 (see *Upstream we are waiting on* below for what to do when they land). **iOS has none of these problems and needs no equivalent guard:** AlarmKit alerts are system-rendered, there is no notification to swipe, no app is opened, and iOS ships no API for showing an app over the Lock Screen at all — tapping a notification there always authenticates first. Neither Runner project has a notification-content or widget extension (8 targets each, Runner + RunnerTests only), so there is no lock-screen surface to audit.
- **Launch soft-fail + iOS checks.initialize (2026-07-21):** Both apps wrap `scheduler.ensureInitialized()` in `on Exception` (never brick cold start on a plugin hiccup; programming `Error`s still propagate). Nivaat's `resync` and `CheckScheduler.initialize` use the same Exception-only policy; location search geocode goes through `reportLocationSearchFailure` (inline “Search failed — check network” for Exceptions; Errors rethrown with stack). Startup goes through `_finishStartup`: **`checks.initialize()` on BOTH platforms** (iOS seeds the periodic BGAppRefresh Dart submit — AppDelegate only registers the handler; Android still defers past the first frame for the AlarmManager race) then `controller.init()`. Don't drop the iOS call when touching Android deferral — burned once in `d7ba843`.
- **AGP is 9.0.1 — plugins that self-apply KGP only under AGP < 9 silently fail to compile their Kotlin (class-not-found in `GeneratedPluginRegistrant`).** Burned by `app_settings` 8.0.0 (2026-07-18): it skips `kotlin-android` on AGP≥9, so `AppSettingsPlugin` never built → both apps' Android builds broke. Fix: dropped it for `url_launcher` (Flutter-team, KGP-clean) for the iOS "Open Settings" (`app-settings:`). **Lesson: after any plugin/native change, `flutter build apk` — `flutter test` does NOT build the Android/iOS native side, so plugin-compile breaks stay invisible.**
- Nivaat Android battery-optimization exemption: `MainActivity` exposes a `nivaat/battery` MethodChannel (`isExempt`/`requestExempt` → `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`); `requestBatteryExemptionOnce()` (in `main`) asks once so off-charger Doze doesn't throttle the cascade's network checks. Needs `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` in the manifest. **`nivaat/battery` is two-sided (2026-07-19): the iOS AppDelegate answers `isExempt` too — there it means "Background App Refresh available" — feeding the same `BackgroundChecksBanner`.**
- **`core/system_settings` MethodChannel (2026-07-19): implemented in BOTH MainActivities** (keep them in sync) — serves core's `openNotificationSettings()` (`ACTION_APP_NOTIFICATION_SETTINGS`; Android's notification page is unreachable by URL, and `permission_handler`/`app_settings`-style plugins are an AGP-9 risk — see below). iOS needs no channel (`app-settings:` URL).
- **`core/app_icon` MethodChannel (2026-07-20): implemented in BOTH MainActivities AND BOTH AppDelegates** (keep all four in sync) — `get`/`set` with icon ids "1"/"2"/"3" (see the app-icons convention bullet). Dev caveat: after switching to a non-default icon on a device, `flutter run`'s explicit `am start …/.MainActivity` fails (component disabled as launcher); fix with `adb shell pm enable com.samyak.<app>/com.samyak.<app>.MainActivity` or switch back to icon 1 in Settings — documented in RUNNING.md troubleshooting.
- Min OS: **Android minSdk 33** (Android 13; set in each `app/build.gradle.kts`) · **iOS deployment target 26.0** (AlarmKit-only ring path; set in each `Runner.xcodeproj/project.pbxproj` and Nivaat's `Podfile`). Nivaat also uses workmanager: the Swift import is `workmanager_apple` (federated module name), plugin class `WorkmanagerPlugin`. **Two iOS BGTask ids** in Info.plist `BGTaskSchedulerPermittedIdentifiers` + registered in `AppDelegate`: `…refresh` (periodic BGAppRefresh, `registerPeriodicTask`) and `…processing` (BGProcessing, `registerBGProcessingTask`). workmanager's `registerProcessingTask(initialDelay:)` **does** set the iOS `earliestBeginDate` (= now+delay); `Constraints.requiresCharging`→`requiresExternalPower`, `networkType:.connected`→`requiresNetworkConnectivity`. BGProcessing is one-shot (no native re-submit) so `scheduleCheck` re-registers it each `evaluateAll`. (`registerOneOffTask`'s `initialDelay` is genuinely ignored on iOS — don't use it for scheduling.)
- AlarmKit: `flutter_alarmkit` takes Flutter asset paths for sounds (WAV < 30s); timestamps are Unix **milliseconds** as double; it assigns its own UUIDs → `AlarmKitScheduler` persists an int-id→UUID map. `NSAlarmKitUsageDescription` required in Info.plist.
- Emulator smoke loop: boot `emulator -avd pixel -no-window`, `adb exec-out screencap -p`. iOS: `xcrun simctl` install/launch/screenshot; seed SharedPreferences by writing the app container's plist while the sim is shut down (simctl spawn defaults writes outside the sandbox — doesn't work). **Both platforms store Flutter prefs under the `flutter.` key prefix** (`flutter.arunoday.settings`, etc.).

- `flutter run` prints a KGP deprecation warning ("plugins that apply Kotlin Gradle Plugin (KGP): alarm") — benign, lives in the `alarm` plugin's own build script, nothing on our side to change; goes away when the plugin migrates to Flutter's built-in Kotlin. Track upstream releases.
- **Never run `dart format` over whole directories (2026-07-20)**: the current SDK ships the new *tall-style* formatter, and the repo predates it — a blanket format rewrote 33 files including untouched ones, drowning the real diff. Match the surrounding (old-style) formatting by hand; if a repo-wide reformat is ever wanted, it must be its own dedicated commit Samyak asks for.

## Upstream we are waiting on (`alarm` package)

Nothing here is forked (see the ring note above), so a fix reaches these apps **only in a pub.dev release — a merged PR changes nothing on the phone.** Two signals, both manual: GitHub notifies Samyak directly — he authored #413, #416 and all three PRs, and commenting on #412 subscribed him to that one; and `flutter pub outdated` in any package prints the latest `alarm` version beside ours. Read the plugin's CHANGELOG before acting on any of them — review can rename or reshape a flag.

- **[#413](https://github.com/gdelataillade/alarm/issues/413) (ours) → PR [#414](https://github.com/gdelataillade/alarm/pull/414) — `NotificationSettings.androidStopAlarmOnDismiss`.** Swiping the ring notification away stops the alarm, because `NotificationService.kt` gives the notification a delete intent that IS the Stop button's `PendingIntent`. The PR adds an opt-out that defaults to today's behaviour. **When a release contains it:** raise the `alarm` constraint in all three pubspecs (and their lockfiles — `flutter pub upgrade alarm` per package; a constraint bump alone leaves the lock pinned), pass `androidStopAlarmOnDismiss: false` in `AlarmPkgScheduler`'s `NotificationSettings`, lock it with a test, and update this file + REVIEW 1.12. **If it is rejected:** delete this entry and nothing else — the behaviour stays as it is, and `RingGate` already puts the app away on any stop, however it was reached.
- **[#412](https://github.com/gdelataillade/alarm/issues/412) (someone else's, we confirmed it) → PR [#415](https://github.com/gdelataillade/alarm/pull/415) — the secure-keyguard prompt.** `AlarmPlugin.kt` calls `requestDismissKeyguard` when a ring starts, which on a PIN/fingerprint device means *authenticate*, so the prompt lands on top of the ring screen. The PR calls it only when `isDeviceSecure` is false. **When a release contains it:** no code change here — the prompt simply stops appearing. **Do not treat it as a reason to revisit the manifests:** they stay bare, and that question is closed, not pending. `android:showWhenLocked` applies to every launch while the lockscreen is up, so it turned each notification into a way past the PIN (device-confirmed 2026-08-02); the ring gets the same flag from the plugin for exactly as long as it sounds, which is the whole of what we wanted. **If it is rejected:** nothing to do — Back dismisses the prompt and the ring screen is underneath.

- **[#416](https://github.com/gdelataillade/alarm/issues/416) (ours) → PR [#417](https://github.com/gdelataillade/alarm/pull/417) — alarm extras on the launcher fallback intent.** The plugin attaches `EXTRA_ALARM_ID` only when an app declares its own `…action.RING` activity; everyone else gets `getLaunchIntentForPackage`, which is byte-identical to tapping the icon. That is the whole reason `kRingForegroundGrace` exists — with the extra, `MainActivity` could read it in `onCreate`/`onNewIntent`, tell Dart over a channel, and `alarmOpenedTheApp` would stop guessing. **When a release contains it:** read the extra natively, pass it through, and **delete the grace constant and its tests** rather than tuning them. **If it is rejected:** keep the heuristic; it is wrong occasionally in a direction that costs a stray hide, not a missed alarm. (This one carries no CHANGELOG entry on purpose — three open PRs on a one-line 5.7.0 section would collide, and all three merge clean without it.)

**On `alarm` 5.6.0 as of 2026-08-02** (published 2026-07-31; 5.5.0 before that): AGP 9 support, Android scheduling / foreground-service / audio crash fixes, iOS timing and background-refresh fixes, a `copyWith` payload fix with some legacy parameters deprecated, and a Dart test suite now run in CI — taken on its own merit and unrelated to any of the three open PRs. **Read a changelog section whole:** this note said Android-only until it was rechecked, because it was written from a `head` of the file that cut off mid-version. Constraint and all three lockfiles raised together. **Both behaviours this repo documents were re-read in the 5.6.0 source, not assumed to carry over** — `setDeleteIntent(stopPendingIntent)` and the unconditional `requestDismissKeyguard` are both still there, so the swipe-stops-alarm and fingerprint-over-the-ring notes above still describe the shipped plugin. **The RING intent path is NOT in 5.6.0** (it landed after, in the unreleased 5.7.0), so #417 is still the route to deleting `kRingForegroundGrace`. Nothing in our Dart touched the changed API surface — analyze is clean and the only rename is a local variable inside the plugin's own `fromJson`. **Still unproven: an actual ring on a device**, which is the one thing a desk can't check, so treat a missed or misbehaving alarm as this upgrade's fault first. Possible follow-up, deliberately not done here: 5.6.0 raises the plugin's own `compileSdk` 34 → 35, which may make the root-gradle reflection override redundant (`flutter_fgbg` needs 35 and now gets it) — that is its own change with its own full build, not a drive-by.
